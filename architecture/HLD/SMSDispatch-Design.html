Throughput Math

Peak = 3,000 msg/hr = 50 msg/min. Each send takes ~3 s. With 16 concurrent Function instances, throughput = 16 ÷ 3 × 60 = 320 msg/min — 6.4× peak capacity. Even at 4 concurrent: 80 msg/min = 1.6× peak. The poll batch of 500 rows per 60-second tick clears a full peak-hour backlog in one cycle.

Third-Party API Downtime (95% uptime)

At 95% uptime, the API is unavailable ~438 hours/year. Messages submitted during downtime stay Queued in the Service Bus subscription. SmsSender will retry up to MaxDeliveryCount=5 with exponential back-off before DLQing. A stale-Queued cleanup job (hourly timer) resets rows stuck in Queued >10 min back to Pending so they re-enter the pipeline on the next poll.

Azure SQL Schema

✓
Matches the given schema exactly — ID, To, From, Message, Status, CreatedDateTime, ModifiedDateTime. Extended with CorrelationId, ProviderStatus, and ProviderMessageId for traceability. 
-- Messages: source of truth for all outbound SMS
CREATE TABLE dbo.Messages (
    Id                  NUMERIC(18, 0)    IDENTITY(1,1)  NOT NULL,
    [To]                NUMERIC(18, 0)   NOT NULL,          -- matches given schema
    [From]              NUMERIC(18, 0)   NOT NULL,
    Message             NVARCHAR(1000)   NOT NULL,
    Status              NVARCHAR(100)    NOT NULL  DEFAULT 'Pending',
    -- Pending → Queued (poller) → Sending → Sent | Failed | DeadLettered
    CreatedDateTime     DATETIME         NOT NULL  DEFAULT GETUTCDATE(),
    ModifiedDatetime    DATETIME         NULL,
    CorrelationId       NVARCHAR(50)     NULL,      -- GUID set when Queued
    ProviderStatus      NVARCHAR(100)    NULL,      -- raw API response status string
    ProviderMessageId   NVARCHAR(100)    NULL,      -- provider-assigned SID
    CONSTRAINT PK_Messages PRIMARY KEY (Id)
);

-- Filtered index: SmsPoller query is Status IN ('Pending') — scans index only
CREATE INDEX IX_Messages_Status_Created
    ON dbo.Messages (Status, CreatedDateTime)
    INCLUDE (Id, [To], [From], Message, CorrelationId)
    WHERE Status IN ('Pending', 'Queued');

-- Search index: SPA "contains/equals" search on Message column
CREATE INDEX IX_Messages_Search
    ON dbo.Messages (CreatedDateTime DESC)
    INCLUDE (Id, [To], [From], Message, Status, ModifiedDatetime);

-- AuditLogs: immutable append-only audit trail
CREATE TABLE dbo.AuditLogs (
    Id              BIGINT           IDENTITY(1,1) NOT NULL,
    MessageId       NUMERIC(18, 0)   NOT NULL,
    EventType       NVARCHAR(50)     NOT NULL,  -- 'Queued'|'Sending'|'Sent'|'Failed'|'DLQ'
    Payload         NVARCHAR(MAX)    NULL,      -- JSON snapshot of SmsEventPayload
    RecordedAt      DATETIME         NOT NULL  DEFAULT GETUTCDATE(),
    CorrelationId   NVARCHAR(50)     NULL,
    CONSTRAINT PK_AuditLogs PRIMARY KEY (Id),
    CONSTRAINT FK_AuditLogs_Messages
        FOREIGN KEY (MessageId) REFERENCES dbo.Messages(Id)
);
CREATE INDEX IX_AuditLogs_MessageId ON dbo.AuditLogs (MessageId);

Single Page Application — Spec

📋
All required front-end features from the problem statement are listed below with how each is implemented.
  • Search / filter string input — Text input above the grid. Bound to reactive form. Query triggered only after ≥3 characters (debounced 300 ms). Matches on Message (contains/equals), To number, From number.
  • Min 3 characters before search — valueChanges.pipe(filter(v => v.length >= 3 || v.length === 0), debounceTime(300)) — empty input shows all records.
  • Contains / Equals toggle — Radio buttons or a dropdown above the grid pass matchType=contains|equals to the API.
  • Grid reorderable by column — Clickable column headers for: Message, To, From, Status, Submitted On (CreatedDateTime), Modified On (ModifiedDatetime). Arrow icons indicate sort direction. Sends sortBy + sortDir to API.
  • Pagination — Page size selector (10/25/50/100). Prev / Next / numbered page links. Shows "Showing 26–50 of 412 results".
  • Clean, easy to understand — Grid view with status badges (colour-coded), phone number formatting, message preview truncated to 80 chars with full-text tooltip. Status polling for the most recently submitted record.
  • Responsive — Mobile: stacked cards instead of table. Tablet/Desktop: full table with sticky column headers.

Error Handling Strategy

SQL Query Failure — Poller
Rethrow from SmsPoller.Run(). Timer retries on next 60-second tick. No rows marked Queued, no messages published. Safe to retry.
Service Bus Publish Failure
Rows already marked Queued. A stale-Queued cleanup job (hourly TimerTrigger) resets rows stuck in Queued >10 min back to Pending automatically.
Deserialization Error — Sender
Log error and complete the message (don't rethrow). A malformed message will never succeed — retrying wastes DLQ slots. Alert on this pattern in Application Insights.
SMS API HTTP Failure — transient
Rethrow from SmsSender. Service Bus retries up to MaxDeliveryCount=5 with back-off. After 5 failures → DLQ → DeadLetterHandler marks row Failed.
SMS API — permanent failure
"Not Sent – Not a valid phone" / "Not Sent – Not valid by Time zone" are permanent. Call PUT /status with Failed immediately; do not rethrow (no retry needed). Complete the message.
SQL Status Update Failure — Sender
Log error, do NOT rethrow. SMS was already sent — retrying would double-send. Row stays in Sending; reconciliation job fixes stale Sending rows after N minutes.
Audit Log Write Failure
Rethrow from SmsAuditLogger. Retries independently of SmsSender (separate subscription). Audit DLQ is separate — audit failure never blocks SMS delivery.
Dead-Letter Queue
Each subscription has its own DLQ. Monitor with Application Insights alert: ActiveMessages >0 on */$DeadLetterQueue. Operator inspects, resets row to Pending, resubmits.
